    01

    Executive view

    CloudSight is a cost observability platform for cloud and AI spend. It helps leadership know where money is going, helps Finance close the month with better evidence, and helps Engineering find which service, endpoint, region, model, team, or customer is driving cost.

    The product is built around one idea: cost data should be observable like reliability data. Every metric should have a source, every row should be traceable, and every report should be generated from normalized telemetry rather than manual spreadsheet stitching.

    02

    Client outcomes

    • Visibility: one dashboard for total spend, requests, services, and top cost drivers.
    • Explainability: endpoint-level usage rows with tags, region, environment, and source reference.
    • Finance readiness: reports, exports, budget summaries, and allocation views from the same data.
    • Trust: audit trail from provider signal to collector to CloudSight storage and readback.
    • Action: identify waste, anomalies, owner teams, and optimization opportunities.
    03

    Evaluation principle

    A serious client should not start by giving broad cloud permissions. They should first run a dry-run proof. CloudSight can replay realistic AWS, GCP, Azure, OpenAI, or internal-service events into the collector contract without creating cloud resources. That proves ingestion, normalization, dashboards, reports, and audit before production access is considered.

    Domain Model

    Core objects a client should understand

    Workspace
    The client tenant. It owns users, roles, collectors, reports, API keys, settings, and usage rows.
    Collector
    A provider-specific adapter that runs in a controlled environment and converts provider signals into CloudSight events.
    Usage row
    A normalized cost and usage record with provider, service, endpoint, units, cost, region, environment, timestamp, tags, and source reference.
    Audit event
    Evidence that provider collection, collector dispatch, CloudSight ingestion, verification, or report readback happened.
    Report
    A finance or operations-ready statement generated from normalized rows, filters, and workspace policy.

    Integration Blueprint

    How a client starts from scratch

    The recommended path moves from zero-risk proof to production telemetry in controlled stages.

    Stage 1

    Discovery and scope

    Confirm providers, billing accounts, subscriptions, projects, regions, environments, teams, tags, reports, dashboards, security constraints, and success criteria. This stage defines what "working" means before any collector is connected.

    Stage 2

    Dry-run proof

    Replay saved provider-like events through the CloudSight API and collector contract. Validate captured rows, raw JSON, audit trail, dashboards, reports, allocation, and usage charts without cloud provider writes or charges.

    Stage 3

    Collector deployment

    Run the collector as a container, scheduled job, serverless function, private service, or customer-managed integration. Supply provider credentials locally and issue a scoped CloudSight collector key.

    Stage 4

    Production validation

    Compare CloudSight output against provider console samples, billing export rows, or known service totals. Enable scheduled reports only after source references, units, costs, and tags are accepted by Finance and Engineering.

    Security And Governance

    Controls a client security team expects

    The design should be easy to review because responsibilities are separated clearly.

    Least privilegeProvider access starts read-only or event-only. No broad admin role is required for standard telemetry.
    Credential separationCloud provider secrets live in the collector runtime, not in the CloudSight UI.
    Scoped API keysCollector keys can be issued per provider, rotated, disabled, and tied to a workspace.
    Tenant isolationUsers, rows, reports, API keys, collectors, and settings are workspace-owned.
    Audit evidenceRows can be traced by sourceReference, batchReference, collector, provider, and timestamp.
    Operational controlsHealth checks cover API, database, collectors, ingestion freshness, backup freshness, and smoke tests.
    AreaClient ownsCloudSight owns
    Provider credentialsCreation, storage, rotation, least privilegeNever requires broad provider admin secrets
    Collector runtimeNetwork, deployment, logs, secret storeReference collector, schema, retry guidance
    Telemetry contractCorrect source mapping and tagsValidation, storage, reports, readback, audit
    Business adoptionOwners, cost centers, report recipientsDashboards, exports, workflow surfaces

    Implementation roles

    • Client cloud admin: creates read-only roles and export permissions.
    • Client platform engineer: deploys collector and owns runtime logs.
    • FinOps owner: validates reports, tags, allocation, and budget rules.
    • CloudSight admin: manages workspace, users, API keys, and onboarding state.

    Proof checklist

    • Collector receives a sample event.
    • CloudSight stores a usage row.
    • Raw JSON matches expected provider/service fields.
    • Audit trail shows provider, collector, ingestion, and verification steps.
    • Dashboard, usage explorer, report, and allocation views reflect the event.
    • Dry-run passes before any real provider write action is enabled.

    Common client questions

    Do you need write access to our cloud?
    No for standard telemetry. The dry-run proof uses sample events. Production should start with read-only or event-forwarding access.
    Where do credentials live?
    Provider credentials should live in the client collector runtime. CloudSight receives normalized events over HTTPS.
    Can this support custom internal services?
    Yes. Any internal system can send the same usage event contract with service, endpoint, units, tags, and source reference.
    How do we prove numbers are correct?
    Use captured rows, raw JSON, readback, audit trail, and reports from the same source reference.
