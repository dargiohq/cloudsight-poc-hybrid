    Client Architecture Guide

    CloudSight from first question to production telemetry

    This page is a complete client-facing guide for CloudSight: what problem it solves, how the collector architecture works, how a customer integrates from scratch, what data is stored, and how teams prove value before they connect real cloud accounts.

    3Clouds in one model
    1Normalized cost stream
    0Provider writes required for dry-run proof
    01

    Why CloudSight exists

    Cloud cost data is usually late, fragmented, and hard to trust. Finance sees invoices after the spend happened. Engineering sees service metrics without normalized unit economics. Leadership sees summaries that hide which API, team, provider, or endpoint actually moved the bill.

    CloudSight gives every team one collector-first telemetry layer for cloud and AI spend. The goal is not only reporting. The goal is fast cost observability: detect usage, normalize it, prove it with audit evidence, and make optimization work actionable.

    02

    What the client gets

    • Executive dashboard for total spend, request volume, active services, and top service share.
    • Usage explorer for provider, service, endpoint, region, environment, and date-range analysis.
    • Reports for finance statements, budget summaries, allocation reports, and custom exports.
    • Audit trail showing provider event, collector receipt, CloudSight ingestion, and readback.
    • Workspace controls for roles, API keys, collectors, policies, billing posture, and settings.
    03

    What makes it different

    CloudSight starts with collectors rather than screenshots or manual invoice upload. A collector can receive provider events, transform them into CloudSight's usage contract, and send them to the platform with a scoped API key. The same data then powers dashboard cards, charts, reports, allocation, unit economics, and audit evidence.

    Reference Architecture

    How data moves through CloudSight

    The client controls provider credentials. CloudSight stores normalized cost telemetry and proof metadata.

    Client Cloud AWS, GCP, Azure, Oracle, OpenAI, custom apps
    Collect
    CloudSight Collector Receives events, maps endpoints, adds context
    Normalize
    CloudSight API Validates API key, writes usage, records audit
    Analyze
    CloudSight App Dashboards, reports, alerts, allocation
    Important for security reviews: CloudSight does not need broad production admin access. The preferred integration is a least-privilege read or event-forwarding setup, with provider credentials staying in the client's environment.

    Core objects

    Workspace
    The client tenant. It owns users, collectors, reports, API keys, and usage rows.
    Collector
    A provider-specific adapter that converts cloud signals into CloudSight events.
    Usage row
    A normalized cost and usage record with provider, service, endpoint, units, region, tags, and source reference.
    Audit event
    Proof that a provider call, collector dispatch, ingestion, or readback happened.
    Report
    A finance or operations-ready summary generated from normalized usage rows.

    Client onboarding journey

    1. Discover: agree on cloud providers, regions, billing accounts, teams, and reporting goals.
    2. Create workspace: invite admins, configure roles, and confirm timezone and default currency.
    3. Issue collector key: generate a scoped key for each provider collector.
    4. Run dry-run: replay sample events to prove ingestion without provider charges.
    5. Connect provider: add read-only credentials, export hooks, or event-forwarding routes.
    6. Validate dashboards: confirm rows, charts, reports, alerts, and audit trail.
    7. Go live: schedule reports, enable policies, and assign owners for optimization work.
    Integration Blueprint

    How a client starts from scratch

    1. Prepare provider access

    Start with read-only or event-only access. For AWS this can be Cost Explorer, CloudWatch, CloudTrail, S3 inventory, and service-specific APIs. For GCP this can be Billing Export, Cloud Storage, BigQuery, Cloud Run, and audit logs. For Azure this can be Cost Management, Monitor, Blob Storage, VM usage, and subscription metadata.

    2. Install or host collector

    The collector can run as a container, serverless function, scheduled job, or private service. The client supplies provider credentials locally. The collector sends only normalized usage events to CloudSight over HTTPS.

    3. Send CloudSight events

    Each event contains provider, service, endpoint, units, timestamp, region, environment, and source reference. Optional tags attach team, product, customer, project, cost center, or owner.

    4. Verify business outputs

    The client checks the captured row, raw JSON, audit trail, usage explorer, dashboard widgets, reports, allocation, and unit economics. The proof is complete only when the same event can be traced from provider signal to CloudSight insight.

    Security And Governance

    Controls a client security team expects

    Least privilegeCollectors use scoped provider access and scoped CloudSight API keys.
    Tenant isolationUsage rows, reports, API keys, and users belong to a workspace.
    Credential separationProvider secrets stay with the client collector runtime.
    TraceabilityEach row can reference the source event, batch, collector, and audit log.
    Retention policyClients define retention, export cadence, and audit requirements.
    Operational healthStatus checks cover API, database, collectors, ingestion, and backup freshness.

    Implementation roles

    • Client cloud admin: creates read-only roles and export permissions.
    • Client platform engineer: deploys collector and owns runtime logs.
    • FinOps owner: validates reports, tags, allocation, and budget rules.
    • CloudSight admin: manages workspace, users, API keys, and onboarding state.

    Proof checklist

    • Collector receives a sample event.
    • CloudSight stores a usage row.
    • Raw JSON matches expected provider/service fields.
    • Audit trail shows provider, collector, ingestion, and verification steps.
    • Dashboard, usage explorer, report, and allocation views reflect the event.
    • Dry-run passes before any real provider write action is enabled.

    Commercial story

    CloudSight is positioned as a cost observability system for engineering and finance together. It reduces surprise bills, shortens finance reconciliation, helps teams understand API-level cost drivers, and creates a repeatable path from raw cloud signals to board-ready reporting.

    Common client questions

    Do you need write access to our cloud?
    No for standard telemetry. The dry-run proof uses sample events. Production should start with read-only or event-forwarding access.
    Where do credentials live?
    Provider credentials should live in the client collector runtime. CloudSight receives normalized events over HTTPS.
    Can this support custom internal services?
    Yes. Any internal system can send the same usage event contract with service, endpoint, units, tags, and source reference.
    How do we prove numbers are correct?
    Use captured rows, raw JSON, readback, audit trail, and reports from the same source reference.
